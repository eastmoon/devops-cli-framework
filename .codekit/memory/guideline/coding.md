# Linux Shell Script 程式撰寫指南 (Coding Guideline)

> 適用語言 (PROGRAM_LANGUAGE)：Linux Shell Script（`sh` / `bash`，需兼顧 POSIX 相容性與 `shellcheck` 靜態分析慣例）
> 本指南依據「程式指南憲章」(.codekit/memory/constitution/coding-guideline.md) 與「程式設計憲章」(.codekit/memory/constitution/software-design.md) 之原則，針對 Linux Shell Script 之語法特性與慣例逐條詮釋為可執行的撰寫規則。

## 程式撰寫規則 (Coding Rules)

Shell Script 缺乏類別、介面、例外拋出等物件導向機制；本節所有規則之詮釋皆以函式 (function)、獨立腳本檔案 (`.sh`)、退出碼 (exit code)、`trap`、`set` 選項等 Shell 原生機制為基礎，不得引入 Shell 不具備之語言構造。

### I. 整潔程式碼 (Clean Code)

程式碼首先是寫給人閱讀，其次才是給機器執行；可讀性與可維護性優先於精簡的字元數。以下條目對應「程式指南憲章」I.1–I.11。

#### I.1 命名 (Naming)
- 環境變數與全域常數採 `UPPER_SNAKE_CASE`（如 `LOG_LEVEL`、`DEPLOY_ENV`）；區域變數與函式名稱採 `lower_snake_case`（如 `parse_args`、`retry_count`）。
- 布林語意變數／函式須以 `is_`、`has_`、`should_` 等前綴表達真偽（如 `is_authorized`、`has_lockfile`），避免以 `flag`、`status` 等模糊命名。
- 禁止使用無意義縮寫（如 `tmp`、`d2`、`mgr`）；`shellcheck` 對過短變數名不會警告，須由審查把關，不得因工具未報錯而放行含糊命名。
- 同一概念（如「設定檔路徑」）於整個專案中須使用一致的變數名稱，不得在不同腳本中分別命名為 `CONF`、`CFG_FILE`、`CONFIG_PATH`。

理由：Shell 變數無型別標註，命名是讀者判斷變數用途與內容型態（路徑／旗標／數值）的唯一線索，命名混亂的成本會隨腳本被引用次數而放大。

#### I.2 函式設計 (Function Design)
- 每個函式只做一件事，函式體以能在單一畫面內閱讀完畢為原則；函式開頭一律使用 `local` 宣告區域變數，避免污染全域命名空間或意外覆寫呼叫端變數。
- 參數個數超過三個時，改以具名變數（呼叫前設定環境變數）或關聯陣列 (`declare -A`) 傳遞，避免呼叫端因位置參數順序錯置造成隱性錯誤。
- 避免以全域變數作為函式輸出參數；函式應透過 `echo`／`printf` 輸出至 stdout 供呼叫端以 `$(...)` 擷取，或以明確的回傳碼 (`return`) 表示結果。
- 避免布林旗標參數（如 `deploy.sh true`）；旗標通常代表函式內部存在兩種不同行為分支，應拆分為兩個獨立函式或子指令（如 `deploy_with_backup` 與 `deploy_without_backup`）。

#### I.3 註解 (Comments)
- 註解用於說明「為什麼 (Why)」（如特定 shell 版本相容性因應、外部系統限制、暫時性因應措施之原因），而非重述指令本身的「做什麼 (What)」。
- 禁止保留與現況不符的過時註解；若使用 `# shellcheck disable=SC參考碼` 停用特定檢查，須於同一行或緊接的註解說明停用理由，不得無理由全面停用檢查規則。
- 禁止以註解暫時停用程式碼區塊（Commented-out Code）作為版本保留手段（如整段 `# old_function() { ... }`）；歷史版本交由版本控制系統（git）負責保留。

#### I.4 格式一致性 (Formatting Consistency)
- 專案內縮排（統一 2 或 4 空白，禁止 Tab／空白混用）、`[[ ]]`（bash）與 `[ ]`（POSIX sh）之使用時機、`function foo()` 與 `foo()` 之函式宣告風格須全專案一致，不得因作者不同而風格各異。
- 格式一致性須以 `shfmt` 自動格式化與 `shellcheck` 靜態檢查於本地或 CI 中強制執行，不得僅依賴人工審查或口頭約定。

#### I.5 重複程式碼 (Code Duplication)
- 相同邏輯出現兩次以上須抽出為共用函式，集中存放於 `lib/`、`shell/utils/` 等共用目錄下的 `.sh` 檔案，並以 `source`（或 `.`）引入，禁止跨腳本複製貼上後修改 (Copy-Paste-Modify)。
- 判斷「重複」以邏輯意圖是否相同為準，而非僅比對指令文字是否相同；不同腳本中恰巧相似但意圖不同的指令序列，不強制合併，避免產生錯誤的耦合。

#### I.6 錯誤訊息與例外 (Error Messages & Exceptions)
- Shell 無例外拋出機制，一律以退出碼 (`exit N` / `return N`) 與寫入 stderr 的錯誤訊息表示失敗；訊息須具體描述失敗原因與上下文（如 `echo "ERROR: config file not found: ${CONFIG_PATH}" >&2`），不得僅輸出「發生錯誤」等泛用訊息。
- 禁止吞噬失敗（如 `some_cmd 2>/dev/null || true` 且無任何記錄）；若刻意忽略某指令失敗，須以註解說明理由，並優先考慮改用 `some_cmd || log_warn "..."` 以保留可觀測性，對應憲章「不得吞噬例外」之要求。

#### I.7 具名常數 (Named Constants)
- 禁止魔術數字／字串（如逾時秒數 `30`、路徑 `/opt/app`）直接寫死於邏輯中，須以 `readonly` 變數定義並賦予語意化名稱（如 `readonly DEFAULT_TIMEOUT_SEC=30`）。
- 具名常數集中定義於腳本頂部或獨立設定檔（如 `constants.sh`），避免同一數值散落於多個腳本中各自重複定義。

#### I.8 巢狀層級 (Nesting Depth)
- `if`／`for`／`while` 巢狀深度超過三層須以衛述句 (Guard Clause)、提前 `return`／`continue`／`exit`，或抽出為獨立函式降低複雜度。
- 對不合法輸入或邊界條件，優先於函式開頭以衛述句提前 `return 1` 或 `exit 1`，保留函式主體用於處理主要邏輯路徑，避免驗證邏輯與主要流程邏輯交錯巢狀。

#### I.9 單一抽象層次 (Single Level of Abstraction)
- 主流程函式（如 `main`）應讀起來像步驟目錄，僅呼叫具語意的高階函式（如 `parse_args "$@"`、`validate_env`、`run_deploy`），逐欄位字串處理、`sed`／`awk` 細節等低階實作須下沉至各自的輔助函式中。
- 禁止在同一函式內混雜高階流程呼叫（如「驗證環境」）與低階實作細節（如逐行文字比對），使高階流程與低階細節分處不同函式。

#### I.10 副作用最小化 (Minimizing Side Effects)
- 命名為 `get_*`、`is_*`、`calculate_*` 的函式僅能查詢並透過 stdout／回傳碼回報結果，不得夾帶修改全域變數、寫入檔案等隱藏副作用（Command-Query Separation）。
- 會修改狀態的函式須以明確動作動詞命名（如 `update_config`、`remove_lockfile`、`save_report`），使呼叫端能預期其副作用。

#### I.11 死碼移除 (Dead Code Removal)
- 未使用的函式、變數與被註解封存的舊程式碼須移除，不得留存於版本控制中；`shellcheck` 之 `SC2034`（未使用變數）等警告須視為須修正項目，不得長期忽略或全域停用該檢查。

### II. 防禦性程式設計 (Defensive Programming)

Shell 腳本經常直接處理使用者輸入、環境變數與外部指令輸出，須假設此類資料可能不符預期，並在邊界主動驗證與防護。以下條目對應「程式指南憲章」II.1–II.10。

#### II.1 輸入驗證 (Input Validation)
- 所有跨越信任邊界的輸入（位置參數 `$@`、環境變數、設定檔內容）須於進入點（`main` 或 `parse_args`）驗證：使用 `${VAR:?錯誤訊息}` 確保必要變數存在且非空，使用 `${VAR:-default}` 為可選變數提供預設值，拒絕不合法輸入並輸出明確錯誤訊息。
- 所有變數展開須加雙引號（如 `"$var"`、`"$@"`），避免因未加引號的展開造成字詞分割 (word splitting) 或路徑萬用字元展開；此類疏漏亦是 Shell 腳本中指令注入風險的主要來源，須避免使用 `eval` 處理未經驗證之外部輸入。
- 驗證邏輯集中於進入點執行一次，內部函式可信任已驗證之資料，避免重複驗證造成邏輯雜訊。

#### II.2 快速失敗 (Fail Fast)
- 腳本開頭一律宣告 `set -euo pipefail`：`-e` 於指令失敗時立即終止、`-u` 於引用未定義變數時報錯、`-o pipefail` 使管線中任一階段失敗即視為整體失敗，避免不合法狀態悄悄流入後續邏輯。
- 若特定指令預期可能失敗且已妥善處理，須以明確的 `if ! cmd; then ...; fi` 或 `cmd || handle_error` 表達，不得依賴無節制的 `|| true` 掩蓋錯誤，使錯誤發生的時間點盡可能貼近錯誤發生的位置。

#### II.3 前置與後置條件 (Pre/Post-conditions)
- 關鍵函式於開頭以明確檢查表達前置條件（如必要指令是否存在、必要參數個數是否足夠、必要檔案是否可讀），不合法即立即 `return 1` 或呼叫錯誤處理函式，而非以隱性假設存在於作者腦中。
- 函式回傳前應確保後置條件成立（如產生的檔案確實存在、必要變數確實已設定），可於函式尾端加入驗證陳述式作為輕量斷言，使違反契約的呼叫能立即被發現。

#### II.4 最小權限 (Least Privilege)
- 僅在必要指令前使用 `sudo`，禁止整支腳本以 root 身分執行僅因其中一小段邏輯需要提權；高權限操作須集中於明確定義的邊界函式，避免權限散落於多處難以稽核。
- 建立之檔案／目錄須以最小必要權限設定（明確 `umask` 或 `chmod`），避免預設權限過於寬鬆；不對外暴露之暫存檔案應限制為擁有者可讀寫（如 `chmod 600`）。

#### II.5 不可變性 (Immutability)
- 定義後不應變動的變數（設定常數、程式版本號）以 `readonly` 宣告，降低後續邏輯誤重新賦值之風險。
- 傳遞陣列／關聯陣列給函式時，若呼叫端資料不應被修改，函式內部應以區域複本操作（如 `local -a copy=("${arr[@]}")`），而非直接修改呼叫端傳入之全域陣列參照。

#### II.6 邊界防護 (Boundary Protection)
- 呼叫外部系統（網路請求、資料庫指令、遠端服務）須設定逾時，如 `curl --max-time 10`、`timeout 30 some_cmd`，不得假設外部呼叫必然於合理時間內回應。
- 對外部呼叫失敗須有明確因應策略（重試、降級為預設值、回報錯誤並結束），透過檢查 `$?` 或 `if ! cmd; then ...` 處理，不得任由呼叫端無限期等待或未經處理即中止整個流程。

#### II.7 明確的失敗模式 (Explicit Failure Mode)
- 函式與腳本以退出碼明確區分「正常結果」與「失敗」（成功 `0`，失敗 `1`–`125`，避免使用 `126`–`165` 等 shell 保留範圍），不得以未文件化的輸出字串（如印出 `"ERROR"` 卻回傳 `0`）表示失敗。
- 專案內退出碼語意須一致並文件化（如於腳本頭部註解列出 `Exit 1: 參數錯誤`、`Exit 2: 設定檔缺失`），避免同一專案內不同腳本對相同數值賦予不同意涵而無明確規範。

#### II.8 資源管理 (Resource Management)
- 使用 `mktemp` 建立暫存檔／目錄，並於腳本開頭以 `trap 'cleanup' EXIT` 註冊清理函式，確保無論正常結束或中途失敗（`INT`、`TERM`）皆會釋放暫存檔、鎖檔與背景行程，不得依賴腳本自然結束間接釋放。
- 開啟之檔案描述符（如 `exec {fd}<file`）須於使用範圍結束時明確關閉（`exec {fd}<&-`），資源釋放邏輯須涵蓋例外路徑（`trap` 涵蓋非正常結束情境），確保發生錯誤時資源仍會被釋放。

#### II.9 防禦第三方相依 (Defending Against Third-Party Dependencies)
- 呼叫外部指令前以 `command -v tool_name >/dev/null 2>&1 || { echo "缺少必要指令: tool_name" >&2; exit 1; }` 確認其存在，不得假設執行環境必然安裝該工具。
- 對外部指令之輸出（如 `jq`、`curl` 回傳的 JSON）須驗證其格式與內容是否符合預期（如檢查指令是否成功解析、必要欄位是否存在），不得盲目信任外部回傳結果的型別與範圍。
- 對第三方指令之呼叫應封裝於專屬的包裝函式之後（如 `curl_json_get()`，對應軟體設計憲章之依賴反轉原則），使其行為異常時只需於單一位置調整因應邏輯。

#### II.10 並行安全 (Concurrency Safety)
- 多個腳本實例可能並行存取的共用資源（鎖檔、共用暫存檔、日誌檔）須以 `flock` 等機制取得鎖後才存取，禁止假設腳本必然循序執行。
- 對共用檔案的寫入須採原子操作（先寫入暫存檔再以 `mv` 取代目標檔），避免並行寫入造成檔案內容損毀；腳本頭部註解須明確標註該腳本是否支援並行執行，避免呼叫端誤用於非預期的並行情境。

## 設計限制 (Design Constraints)

Shell Script 無原生類別、介面或型別系統，僅具備函式、獨立腳本檔案與 `source`／`.` 引入機制。以下條目依「程式設計憲章」七大原則，詮釋其在 Shell Script 情境下的具體實踐方式，不得引入類別繼承、介面實作等 Shell 不支援的語言構造。

### I. 單一職責原則 (Single Responsibility Principle, SRP)
- 一個腳本檔案或一組函式僅對應一項職責（如 `deploy.sh` 只負責部署流程、`validate.sh` 只負責驗證邏輯），判斷依據為「導致其變更的原因」是否單一，而非腳本行數多寡。
- 若一個腳本同時處理設定解析、業務邏輯與輸出格式化，須拆分為獨立腳本或函式群組（如拆出 `parse_config.sh`、`format_output.sh`）；修改輸出格式邏輯不應波及設定解析邏輯，修改後的各單元須可獨立以參數／stdin 測試。

### II. 開放封閉原則 (Open/Closed Principle, OCP)
- 新增行為以新增獨立腳本檔案或新增函式達成，既有已通過測試的腳本邏輯應維持不變；例如新增一種部署目標時，新增 `deploy_target_k8s.sh` 而非修改既有 `deploy_target_vm.sh` 的內部邏輯。
- 隨子指令增加而持續增長的 `case`／連續 `if-elif` 分派邏輯，應改以「子指令名稱對應函式名稱」之慣例（如呼叫 `"cmd_${subcommand}"`）取代條件分支持續擴增；新增子指令僅需新增對應函式，但函式名稱之組成須先經白名單或 `case` 驗證後才可呼叫，禁止將未經驗證之外部輸入直接組入 `eval` 或指令執行，以避免注入風險。
- 已發布供其他腳本呼叫的函式簽章（參數順序、回傳碼語意）一旦發布不可隨意變更；如需變更須先標記棄用、提供相容包裝函式，經確認無呼叫端受影響後才可移除。

### III. 里氏替換原則 (Liskov Substitution Principle, LSP) — 以統一函式呼叫慣例取代子型別替換
- 同一類用途的函式（如所有 `validate_*` 驗證函式、所有 `deploy_target_*` 部署函式）須遵循一致的參數順序與回傳碼語意（成功回傳 `0`、失敗回傳非零並可選擇性輸出訊息至 stderr），使呼叫端可任意替換其中一個實作而不需為特定實作撰寫特殊處理邏輯。
- 新增或替換某個函式實作時，不得比原實作要求更嚴格的輸入條件（如原本接受相對與絕對路徑，替換版本卻只接受絕對路徑），也不得提供比原實作更弱的輸出保證或改變其預期副作用範圍（如原本不寫檔的驗證函式，替換版本不應新增寫檔副作用）。

### IV. 介面隔離原則 (Interface Segregation Principle, ISP) — 以拆分小型工具腳本取代介面拆分
- 大型、多用途的腳本應依使用情境拆分為多個小型單一用途的 `.sh` 工具檔（如將涵蓋日誌、驗證、部署的單一巨型腳本拆為 `lib/log.sh`、`lib/validate.sh`、`deploy.sh`），使呼叫端僅需 `source` 其實際需要的檔案，而非被迫載入整個大型腳本的所有函式。
- 共用函式庫腳本不得包含「尚未實作」的空函式或僅印出提示訊息的佔位函式；若某函式庫檔案中頻繁出現多數呼叫端用不到的函式，代表其職責範圍（介面粒度）過大，須進一步依使用情境拆分為更細的檔案。

### V. 依賴反轉原則 (Dependency Inversion Principle, DIP) — 以環境變數／參數注入取代直接依賴
- 函式或腳本所依賴的外部指令、路徑、設定值須透過環境變數或函式參數注入（如 `readonly CURL_BIN="${CURL_BIN:-curl}"`），不得於函式內部寫死呼叫特定路徑或特定實作（如寫死 `/usr/local/bin/mycurl`）。
- 高階業務邏輯腳本不得直接依賴特定基礎設施工具的具體呼叫方式，應透過封裝函式（如 `http_get()` 內部決定實際使用 `curl` 或 `wget`）存取外部工具；替換底層工具時僅需調整封裝函式，高階呼叫端邏輯無須變動。

### VI. 高內聚，低耦合 (High Cohesion, Low Coupling)
- 依主題劃分目錄與檔案（如 `kind/`、`shell/`、`utils/`），同一目錄下的腳本／函式須圍繞同一組職責，禁止將不相關功能塞入同一檔案僅為共用檔名或命名空間。
- 模組（腳本檔案）之間僅能透過明確的函式介面（`source` 後呼叫具名函式）溝通，禁止直接讀取或修改其他腳本檔案內部未公開之變數；跨檔案共用之變數須於註解中明確標示為對外公開介面的一部分。
- 修改一個腳本檔案的內部實作（函式內部邏輯），不得要求同步修改其他腳本檔案的內部實作（僅允許透過函式介面調整）；若修改內部實作卻需連帶修改其他腳本的內部邏輯，代表耦合過高，須重新檢視共用介面設計。

### VII. 隔離關注點 (Separation of Concerns, SoC)
- 依關注點分層組織目錄（如呈現層 `cli/` 負責參數解析與輸出格式化、應用邏輯層 `commands/` 負責流程協調、基礎設施層 `lib/` 負責外部指令包裝），禁止呈現層腳本直接組裝底層指令字串或直接操作基礎設施細節。
- 跨領域關注點（記錄 Logging、輸入驗證、快取）應抽出為共用函式庫（如 `lib/log.sh`、`lib/validate.sh`）並以 `source` 引入，不得於各業務腳本中重複撰寫相同的記錄或驗證邏輯。
- 各層腳本僅能透過定義好的函式介面與相鄰層溝通（如應用層呼叫基礎設施層封裝函式，而非直接呼叫原生指令），不得讓上層腳本直接持有或依賴下層腳本的內部實作細節（如寫死的暫存檔路徑格式）。

## Governance

- 修訂程序：修訂者提出變更原因、受影響範圍，經專案負責人核准後生效並記錄於版本歷程。
- 版本控制政策：採語意化版本 (Semantic Versioning)。
  - 主版本：規則群組（程式撰寫規則／設計限制）增刪或重新定義，屬不相容變更。
  - 次版本：新增具體規則、章節，或大幅擴充既有規則之指導方針。
  - 修訂版：措辭澄清、錯字修正等非語意性變更。
- 合規性審查：程式碼審查須依「程式撰寫規則」與「設計限制」兩章節逐項核對 Shell 腳本是否符合整潔程式碼、防禦性程式設計，以及七大軟體設計原則之 Shell 情境詮釋；違反者須修正或於審查紀錄中載明理由後始得合併。
- 本指南所有規則之詮釋皆以 Linux Shell Script（`sh`／`bash`）語法與 `shellcheck`／`shfmt` 慣例為邊界，不得於本指南中引入類別、介面、例外拋出等 Shell 不具備之語言機制；如遇 Shell 語法無法對應之憲章條目，須以退出碼、`trap`、`||`／`&&` 等 Shell 慣用錯誤處理機制重新詮釋，不得直接照搬物件導向語言之措辭。
