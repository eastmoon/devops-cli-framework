# 程式編寫指南憲章 (Coding Guideline Constitution)

## Core Principles

### I. 整潔程式碼 (Clean Code)
程式碼首先是寫給人閱讀，其次才是給機器執行；可讀性與可維護性優先於精簡的字元數。以下各子章節將此原則展開為具體、可審查的條目。

#### I.1 命名 (Naming)
命名是程式碼中出現頻率最高的溝通行為，命名品質直接決定他人（含未來的自己）理解程式碼所需的時間。
- 變數、函式、類別命名須清楚表達其意圖與用途，讀者不應需要開啟定義處或詢問作者才能理解其含義。
- 禁止使用無意義縮寫（如 `tmp`、`data2`、`mgr`）或需額外註解才能理解的命名；若命名須靠註解補充說明才可理解，應優先重新命名而非新增註解。
- 布林變數與函式命名須能直接表達真偽語意（如「是否已授權」而非「狀態」），避免讀者需反查判斷邏輯才能得知其意涵。
- 同一概念於整份程式碼中須使用一致的詞彙，禁止在不同模組對同一概念使用不同名稱（如同時使用 `Customer` 與 `Client` 指稱同一實體）。

理由：命名錯誤或含糊的成本會隨程式碼被閱讀次數而累積放大，是最低成本、最高報酬的整潔程式碼實踐。

#### I.2 函式設計 (Function Design)
函式是程式碼組織的基本單位，其設計品質決定程式碼是否易於理解、測試與重組。
- 每個函式只做一件事，函式長度以能在單一畫面內閱讀完畢為原則；若函式內出現以空行或註解分隔的多個邏輯區塊，即為應拆分之訊號。
- 參數個數過多（超過三個）時，須改以物件或結構封裝傳遞，避免呼叫端因參數順序錯置而產生隱性錯誤。
- 函式應避免輸出參數 (Output Parameter) 與布林旗標參數 (Boolean Flag Parameter)；旗標參數通常代表函式內部存在兩種不同行為分支，應拆分為兩個獨立函式。

#### I.3 註解 (Comments)
註解是程式碼的補充說明，其存在本身即隱含著程式碼未能完全自我表達之處，須謹慎且有目的地使用。
- 註解用於說明「為什麼 (Why)」（如業務限制、暫時性因應措施之原因）而非「做什麼 (What)」；「做什麼」應由良好命名與函式結構自我說明。
- 禁止保留過時或與程式碼行為不符的註解；註解與程式碼不同步的風險高於完全沒有註解。
- 禁止使用註解暫時停用程式碼區塊 (Commented-out Code) 作為版本保留手段，此類歷史應交由版本控制系統負責。

#### I.4 格式一致性 (Formatting Consistency)
一致的格式讓讀者將認知資源集中於邏輯本身，而非適應每個檔案不同的排版風格。
- 專案內縮排、括號風格、命名慣例（大小寫規則）須全專案一致，不得因作者不同而風格各異。
- 格式一致性須以自動化格式化工具與靜態檢查工具強制執行，不得僅依賴人工審查或口頭約定。

#### I.5 重複程式碼 (Code Duplication)
重複的邏輯是修改風險的主要來源：修改一處而遺漏其他複本，會導致行為不一致的缺陷。
- 相同邏輯出現兩次以上須抽出為共用函式或模組，禁止複製貼上後修改（Copy-Paste-Modify）。
- 判斷「重複」應以邏輯意圖是否相同為準，而非僅比對程式碼文字是否相同；意圖不同但程式碼恰巧相似者，不強制合併，避免產生錯誤的耦合。

#### I.6 錯誤訊息與例外 (Error Messages & Exceptions)
例外處理的品質決定系統發生問題時，維運與除錯人員能否迅速定位原因。
- 例外處理須具體描述失敗原因與上下文（如涉及的識別碼、輸入值），不得僅拋出泛用訊息（如「發生錯誤」）。
- 不得吞噬例外（silent catch）或使用空的 `catch` 區塊；捕捉例外後若不處理，至少須記錄並重新拋出。

#### I.7 具名常數 (Named Constants)
未命名的字面值會使讀者無從得知其業務意涵，亦難以在多處引用時保持一致。
- 禁止使用魔術數字或魔術字串 (Magic Number / Magic String)，須以具名常數或列舉 (Enum) 取代並賦予語意化名稱。
- 具名常數須集中定義於明確位置（如常數類別、設定檔），避免同一數值散落於多個檔案中各自定義。

#### I.8 巢狀層級 (Nesting Depth)
過深的巢狀結構會使讀者須同時在腦中維護多層條件狀態，是可讀性下降的常見主因。
- 條件與迴圈之巢狀深度不宜過深，超過三層須以提前返回 (Early Return)、衛述句 (Guard Clause) 或抽出函式降低複雜度。
- 對於例外情況（不合法輸入、邊界條件），優先於函式開頭以衛述句提前返回或拋出例外，保留函式主體用於處理主要邏輯路徑。

#### I.9 單一抽象層次 (Single Level of Abstraction)
函式內部若混雜不同抽象層次的陳述式，會迫使讀者在「理解整體流程」與「理解實作細節」之間反覆切換。
- 同一函式內的陳述式應處於相近的抽象層次，禁止在同一函式中混雜高階流程呼叫（如「驗證訂單」）與低階實作細節（如逐欄位的字串比對）。
- 高階流程函式應讀起來像一份步驟目錄，實作細節則下沉至各自的低階函式中。

#### I.10 副作用最小化 (Minimizing Side Effects)
函式名稱是對呼叫端的行為承諾，違背此承諾的隱藏副作用會使程式碼難以推理。
- 函式命名須誠實反映其副作用；若函式名稱僅描述查詢行為（如 `Get`、`Is`、`Calculate`），該函式不得夾帶隱藏的資料修改副作用（Command-Query Separation）。
- 會修改狀態的函式，其命名須明確使用動作動詞（如 `Update`、`Save`、`Remove`），使呼叫端能預期其副作用。

#### I.11 死碼移除 (Dead Code Removal)
無法被執行或引用的程式碼只會增加閱讀與維護負擔，且可能誤導讀者以為其仍在生效。
- 未使用的變數、函式，以及被註解封存的舊程式碼須移除，不得留存於版本控制中；歷史版本可透過版本控制系統的歷史紀錄查閱，無須保留於當前程式碼。

### II. 防禦性程式設計 (Defensive Programming)
程式須假設輸入、外部相依與執行環境可能不符預期，並在邊界主動驗證與防護，而非假設呼叫端必然正確。以下各子章節將此原則展開為具體、可審查的條目。

#### II.1 輸入驗證 (Input Validation)
系統邊界是不可信資料進入系統的第一道關卡，未經驗證的輸入是多數安全與正確性缺陷的根源。
- 所有跨越信任邊界的輸入（使用者輸入、外部 API 回應、設定檔）須於進入點驗證型別、範圍與格式，拒絕不合法輸入並提供明確錯誤訊息。
- 驗證邏輯須集中於邊界進入點執行一次，內部邏輯可信任已驗證之資料，避免重複驗證造成邏輯雜訊（詳見「兩原則之取捨」）。

#### II.2 快速失敗 (Fail Fast)
讓錯誤盡早且明確地浮現，是降低除錯成本最有效的手段之一。
- 偵測到不合法狀態時，須立即拋出例外或終止流程，禁止讓不合法狀態悄悄流入後續邏輯。
- 錯誤發生的時間點應盡可能貼近錯誤發生的位置，避免不合法狀態在系統內傳遞多層後才在不相關的位置引發難以追溯的錯誤。

#### II.3 前置與後置條件 (Pre/Post-conditions)
明確的契約使函式的呼叫端與實作端對「輸入應滿足什麼條件」「輸出保證什麼結果」有一致的理解。
- 關鍵函式的前置條件（輸入假設）與後置條件（輸出保證）須以斷言 (Assertion) 或明確檢查表達，不得僅以隱性假設存在於作者腦中。
- 前置條件檢查應於函式最開頭執行，使違反契約的呼叫能立即被發現，而非等待後續邏輯間接暴露問題。

#### II.4 最小權限 (Least Privilege)
模組或函式取得超出其職責所需的權限或存取範圍，會擴大單一缺陷或漏洞的潛在影響範圍。
- 模組、函式與外部呼叫僅取得完成任務所需的最小權限與存取範圍，禁止預先取得超出當下需求的資源或權限。
- 具備高權限（如資料庫寫入、檔案系統存取）的操作須集中於明確定義的邊界元件，避免權限散落於多處難以稽核。

#### II.5 不可變性 (Immutability)
可變狀態是並行錯誤與非預期副作用的主要來源；不可變資料結構從根本上消除這類風險。
- 能以不可變 (Immutable) 資料結構表達的狀態，優先使用不可變設計，降低非預期的狀態被外部修改之風險。
- 對外暴露的集合或物件參照，若不應被呼叫端修改，須以唯讀介面或防禦性複本 (Defensive Copy) 提供，而非直接暴露內部可變參照。

#### II.6 邊界防護 (Boundary Protection)
對外部系統的呼叫是程式無法完全掌控的環節，須假設其可能逾時、失敗或回傳非預期結果。
- 對外部系統（資料庫、第三方服務、檔案系統）的呼叫須設定逾時 (Timeout) 與例外處理，不得假設外部呼叫必然成功。
- 對外部呼叫失敗之情境須有明確的因應策略（重試、降級、回報錯誤），不得任由呼叫端無限期等待或未經處理即中止整個流程。

#### II.7 明確的失敗模式 (Explicit Failure Mode)
含糊的失敗表示方式會迫使呼叫端猜測其意涵，進而遺漏必要的錯誤處理。
- 函式回傳值須明確區分「正常結果」與「失敗／空值」狀態（例如採用 Result 型別或明確的例外），禁止以未文件化的魔術值（如 `-1`、隱含意義的 `null`）表示錯誤。
- 失敗狀態的表示方式須在同一專案內保持一致（統一採用例外或統一採用可為空型別），不得同一專案內兩種方式混用而無明確規範。

#### II.8 資源管理 (Resource Management)
未釋放的資源會逐漸耗盡系統容量（連線數、檔案控制代碼），且此類缺陷通常在長時間運行後才會顯現。
- 取得之外部資源（檔案控制代碼、連線、鎖）須確保於使用範圍結束時明確釋放，不得依賴垃圾回收機制間接釋放。
- 資源釋放邏輯須涵蓋例外路徑（如使用 `try/finally` 或等效語言機制），確保發生例外時資源仍會被釋放。

#### II.9 防禦第三方相依 (Defending Against Third-Party Dependencies)
外部函式庫或服務的實際行為可能與其文件描述不符，或於版本升級後改變行為，程式不應無條件信任。
- 呼叫外部函式庫或服務時，須驗證回傳值是否符合預期契約，不得盲目信任外部回傳結果的型別與範圍。
- 第三方相依之呼叫應封裝於明確的介面之後（對應軟體設計憲章之依賴反轉原則），以便在其行為異常時能於單一位置調整因應邏輯。

#### II.10 並行安全 (Concurrency Safety)
並行情境下的錯誤通常難以重現與除錯，須在設計階段即以明確假設處理，而非事後補救。
- 共享的可變狀態於多執行緒／並行情境下存取時，須以同步機制（鎖、原子操作、不可變設計）保護，禁止假設呼叫必然循序發生。
- 涉及共享狀態的程式碼須明確標註其並行安全性假設（是否執行緒安全），避免呼叫端誤用於非預期的並行情境。

## 原則取捨 (Principle Trade-offs)

當「整潔程式碼」追求簡潔與「防禦性程式設計」要求周全的邊界檢查產生篇幅衝突時：
- 邊界層（對外輸入、外部呼叫）優先套用防禦性程式設計，允許較多驗證程式碼。
- 內部層（已驗證資料在模組間傳遞）優先套用整潔程式碼原則，避免重複驗證造成雜訊。

## 合規要求 (Compliance Requirements)

依前述各子章節之詮釋，程式碼是否合規須依下列判準逐項核對：

- 命名與可讀性判準（對應 I.1、I.9）：審查者須能在不參考額外註解的情況下，僅憑命名與陳述式的抽象層次理解程式碼意圖；無法理解者視為不合規。
- 函式結構判準（對應 I.2、I.8、I.10）：函式是否僅做一件事、參數是否封裝、巢狀是否超過三層、命名是否誠實反映副作用；任一項不符即須重構或提出例外理由。
- 註解與死碼判準（對應 I.3、I.11）：確認註解僅說明「為什麼」且與現況相符，且不存在被註解封存的程式碼或未使用之程式碼。
- 格式與常數判準（對應 I.4、I.7）：確認格式化工具已於本地或 CI 中強制執行，且不存在未具名之魔術數字或魔術字串。
- 重複程式碼判準（對應 I.5）：確認相同意圖之邏輯未以複製貼上方式存在於兩處以上。
- 例外處理判準（對應 I.6、II.7）：確認所有 `catch` 區塊皆有明確處理、記錄或轉拋，例外訊息含足夠上下文，且失敗狀態之表示方式全專案一致。
- 輸入邊界與快速失敗判準（對應 II.1、II.2、II.3）：對每一個對外公開的 API 或函式，須確認存在對應之輸入驗證邏輯、於偵測到不合法狀態時立即失敗，並提供對應之失敗路徑測試案例；缺漏視為不合規。
- 權限與資源判準（對應 II.4、II.8）：確認模組僅取得任務所需之最小權限，且所有取得之外部資源皆有涵蓋例外路徑的明確釋放邏輯。
- 不可變性與並行判準（對應 II.5、II.10）：確認對外暴露之集合／物件未直接暴露可變參照，且共享可變狀態之並行安全性假設已明確標註。
- 外部相依判準（對應 II.6、II.9）：確認對外部系統與第三方函式庫之呼叫皆設有逾時與例外處理，並封裝於明確介面之後。
- 靜態分析工具強制：專案須於持續整合 (CI) 流程中整合靜態分析工具 (Linter / Analyzer)，違反上列任一判準之程式碼不得合併。
- 例外情況記錄：若程式碼審查中發現違反本憲章之設計，但有明確業務或效能理由，須於審查紀錄中載明理由，並作為後續本憲章修訂之參考依據。

## Governance

- 修訂程序：修訂者提出變更原因、受影響範圍，經專案負責人核准後生效並記錄於版本歷程。
- 版本控制政策：採語意化版本 (Semantic Versioning)。
  - 主版本：原則增刪或重新定義。
  - 次版本：新增具體規則或章節。
  - 修訂版：措辭澄清、錯字修正。
- 合規性審查：程式碼審查須依「合規要求」章節逐項核對是否符合整潔程式碼與防禦性程式設計之具體規則；違反者須修正或載明理由後始得合併。
