# 程式碼摘要憲章 (Code Summarization Constitution)

## Core Principles

### I. 程式理解 (Program Comprehension)
摘要之根本目的在於協助讀者建立與程式實際行為一致的心智模型 (Mental Model)，而非單純轉譯程式碼文字。以下子章節將此原則展開為具體、可審查的條目。

#### I.1 建立正確心智模型 (Building an Accurate Mental Model)
- 摘要須協助讀者形成與程式實際行為一致的心智模型，摘要內容不得與程式碼實際邏輯有出入，否則將誤導讀者形成錯誤預期。

#### I.2 由上而下的理解順序 (Top-Down Comprehension Order)
- 摘要應遵循由整體到細節的呈現順序，先陳述高階目的，再視需要展開細節，對應人類閱讀程式碼時由上而下建立假設、逐步驗證的認知過程。

#### I.3 認知負荷最小化 (Minimizing Cognitive Load)
- 摘要之長度與資訊密度須控制在讀者可負荷之範圍內，避免一次性堆疊過多細節，導致讀者難以在短時間內掌握重點。

### II. 軟體逆向工程 (Software Reverse Engineering)
在缺乏原始設計文件時，摘要須扮演「從既有實作還原設計意圖」的橋樑角色。以下子章節將此原則展開為具體、可審查的條目。

#### II.1 從實作反推設計意圖 (Recovering Design Intent from Implementation)
- 摘要須嘗試從程式碼結構、命名與呼叫關係反推其背後的設計決策與意圖，而非僅描述表面的程式碼排列。

#### II.2 領域概念識別 (Domain Concept Recovery)
- 摘要須識別並標示程式碼中隱含的領域概念（如業務規則、狀態轉換），而非僅描述技術結構。

#### II.3 保留不確定性標註 (Preserving Uncertainty)
- 若程式碼證據不足以確定其原始意圖，摘要須明確標示為推測（如加註「推測用途為...」），不得將推測結果陳述為確定事實。

### III. 程式碼摘要 (Source Code Summarization)
以精簡自然語言描述程式碼片段之功能、目的與脈絡，供人類讀者快速掌握程式碼用途而不必閱讀完整實作。以下子章節將此原則展開為具體、可審查的條目。

#### III.1 目的與功能優先 (Purpose-and-Function-First)
- 摘要須優先描述程式碼片段之目的與對外提供的功能，此為摘要存在之核心價值，不得以次要資訊喧賓奪主。

#### III.2 脈絡涵蓋 (Contextual Coverage)
- 摘要須涵蓋程式碼運作所需之關鍵脈絡（如觸發時機、依賴之外部資源、呼叫前提），避免脫離脈絡的片段描述。

#### III.3 精簡與完整之平衡 (Balancing Conciseness and Completeness)
- 摘要須以最精簡之自然語言達成完整表意，禁止為求精簡而遺漏影響讀者理解之關鍵資訊。

### IV. 意圖提升 (Intent Elevation / What over How)
摘要須陳述程式碼「做什麼／為何存在」，而非逐步複述「如何實作」。以下子章節將此原則展開為具體、可審查的條目。

#### IV.1 禁止逐行複述 (No Line-by-Line Restatement)
- 摘要禁止逐行翻譯程式碼語法（例如「這個迴圈跑過陣列的每個元素」），而須描述該迴圈達成的業務目的（例如「篩選出逾期未付款的訂單」）。

#### IV.2 聚焦行為契約 (Focus on Behavioral Contract)
- 摘要層級須高於程式碼的控制流程層級，聚焦於函式或模組對外承諾的行為契約，而非其內部如何達成該承諾。

#### IV.3 不重複顯而易見的實作 (No Restating the Obvious)
- 若程式碼命名或結構本身已能表達實作方式，摘要不得重複贅述該顯而易見的實作細節。

### V. 去噪與抽象化 (De-noising and Abstraction)
摘要須濾除與核心功能無關的雜訊，並將具體實作抽象為概念層級描述。以下子章節將此原則展開為具體、可審查的條目。

#### V.1 濾除輔助性程式碼 (Filtering Auxiliary Code)
- 日誌記錄、效能監控埋點、防禦性檢查等輔助性程式碼，除非為該片段之核心關注點，否則不納入摘要。

#### V.2 實作細節概念化 (Conceptualizing Implementation Details)
- 具體的變數名稱、迴圈計數器、暫存變數等實作細節，不得直接出現於摘要中，須以其代表的概念取代。

#### V.3 樣板程式碼視為雜訊 (Boilerplate as Noise)
- 重複出現的樣板程式碼（如標準的錯誤處理框架、標準的資源釋放流程）視為雜訊，僅在其偏離標準模式時才需說明。

### VI. 語意分塊 (Semantic Chunking)
摘要須依程式碼的語意邊界分段，而非依實體邊界（如檔案、行數）機械切割。以下子章節將此原則展開為具體、可審查的條目。

#### VI.1 依功能單元劃分 (Division by Functional Unit)
- 分塊依「功能單元」劃分（如一個完整的業務流程、一個職責完整的函式群組），不得在語意未完整表達之處中斷。

#### VI.2 分塊獨立可理解 (Chunk-Level Independence)
- 單一分塊之摘要須能獨立表達完整意涵，不依賴讀者同時參照其他分塊才能理解。

#### VI.3 巢狀結構由外而內展開 (Outside-In Expansion for Nested Structures)
- 巢狀結構（函式內呼叫子函式）之摘要，須先總結最外層之整體目的，再視需要展開內層分塊。

### VII. 領域詞彙映射 (Domain Vocabulary Mapping)
摘要用語須對應至該軟體所屬業務領域之既有詞彙，而非直接沿用程式碼中的技術命名。以下子章節將此原則展開為具體、可審查的條目。

#### VII.1 技術命名轉譯 (Technical-to-Domain Translation)
- 程式碼中的技術性命名（如變數、類別、方法名）須轉譯為該業務領域慣用之詞彙（例如將 `calcDiscRate` 轉譯為「計算折扣率」而非「計算 disc rate」）。

#### VII.2 詞彙一致性 (Terminology Consistency)
- 同一領域概念於摘要全文中須使用一致的詞彙，不得因程式碼中命名不一致而在摘要中出現多種說法指稱同一概念。

#### VII.3 以現行領域詞彙為準 (Current Domain Terminology Precedence)
- 若程式碼命名與領域詞彙有落差（如技術債留下的舊命名），摘要應以現行領域詞彙為準，不遷就過時命名。

## 原則取捨 (Principle Trade-offs)

當本章各原則彼此衝突時，依下列優先順序解決：
1. 當「程式理解」之認知負荷最小化（I.3）與「軟體逆向工程」之領域概念識別（II.2）衝突時（例如完整還原領域概念需要較長篇幅），優先以分層揭露方式處理：摘要主體維持精簡，領域概念細節下沉至可視需要展開之子分塊（對應語意分塊 VI.3），而非直接省略。
2. 當「意圖提升」（IV）與「軟體逆向工程」之保留不確定性（II.3）衝突時（例如意圖不明確，難以直接陳述「做什麼」），優先服從 II.3：以推測性語句陳述並明確標示不確定性，不得為求意圖提升之簡潔而武斷陳述未經證實之意圖。
3. 當「去噪與抽象化」（V）與「程式碼摘要」之脈絡涵蓋（III.2）衝突時（例如某段防禦性檢查依 V.1 應濾除，但該檢查恰為理解呼叫前提所需之脈絡），優先服從脈絡涵蓋：若濾除該資訊將使讀者誤判呼叫前提，則保留之，不機械套用去噪規則。
4. 當「語意分塊」之分塊獨立可理解（VI.2）與「認知負荷最小化」（I.3）衝突時（例如為求分塊獨立完整，須重複陳述前置脈絡），優先接受少量必要的重複陳述，以確保單一分塊仍可獨立理解。
5. 若仍有疑義，優先服務於「讀者能否據此正確理解程式碼行為」此一根本目的，並於摘要文件中說明取捨理由。

## 合規要求 (Compliance Requirements)

依前述各子章節之詮釋，程式碼摘要是否合規須依下列判準逐項核對：

- 心智模型判準（對應 I.1–I.3）：摘要內容是否與程式碼實際行為一致；是否由整體到細節呈現；長度與資訊密度是否適中。
- 逆向還原判準（對應 II.1–II.3）：摘要是否反映程式碼背後之設計意圖與領域概念；不確定之推測是否明確標示，未標示者視為不合規。
- 摘要核心判準（對應 III.1–III.3）：摘要是否以目的與功能為優先；是否涵蓋必要脈絡；是否兼顧精簡與完整。
- 意圖層級判準（對應 IV.1–IV.3）：摘要是否逐行複述程式碼語法；是否聚焦於行為契約而非實作方式。
- 去噪判準（對應 V.1–V.3）：摘要是否納入無關之輔助性程式碼、具體變數名稱或標準樣板細節，出現者視為不合規。
- 分塊判準（對應 VI.1–VI.3）：分塊邊界是否對應完整功能單元；單一分塊是否可獨立理解；巢狀結構是否由外而內展開。
- 詞彙映射判準（對應 VII.1–VII.3）：摘要用語是否已轉譯為業務領域詞彙；同一概念全文用詞是否一致；用詞是否以現行領域詞彙為準。
- 例外情況記錄：若因摘要目的特殊（如技術文件而非業務文件）需保留技術命名或實作細節，須於摘要中明確載明理由，作為後續本憲章修訂之參考依據。

## Governance

本憲章適用於所有程式碼摘要、模組說明文件、以及逆向工程過程中產出之功能說明。

- 修訂程序：修訂者須說明新增或調整之原則及其適用情境，經專案負責人核准後生效。
- 版本控制政策：採語意化版本 (Semantic Versioning)。
  - 主版本：原則增刪或重新定義。
  - 次版本：新增具體指導方針或範例。
  - 修訂版：措辭澄清、錯字修正。
- 合規性審查：產出之程式碼摘要於納入文件前，須依「合規要求」章節確認是否符合上述七項原則，違反者須修正後始得採用。
