# 虛擬碼撰寫憲章 (Pseudocode Writing Constitution)

## Core Principles

### I. 語言無關性 (Language Agnostic)
虛擬碼不得綁定於任何特定程式語言之語法。以下子章節將此原則展開為具體、可審查的條目。

#### I.1 禁用語言專屬語法 (No Language-Specific Syntax)
- 禁止使用特定語言專屬關鍵字或函式庫呼叫（例如 Python 的 `self`、JavaScript 的 `undefined`、Java 的 `public static void main`）。
- 若某段邏輯僅能以特定語言之語法慣例表達，應改以通用的概念性描述取代，而非直接挪用該語言語法。

#### I.2 通用流程控制詞彙 (Universal Control-Flow Vocabulary)
- 流程控制以通用詞彙表達（如 `IF...THEN...ELSE`、`FOR EACH...IN...`、`WHILE...DO`、`RETURN`），不得使用特定語言的大括號區塊語法作為唯一結構依據。

#### I.3 概念性資料型別 (Conceptual Data Types)
- 資料型別以概念性名稱表示（如「整數」「清單」「對應表」），不得使用特定語言的型別關鍵字（如 `int32`、`List<T>`、`dict`）。

理由：虛擬碼的目的是傳達演算法邏輯，若綁定特定語言語法，將限制其可讀性與跨語言實作的可移植性。

### II. 結構清晰，善用縮排 (Clear Structure via Indentation)
虛擬碼須以縮排明確呈現程式區塊的巢狀層級。以下子章節將此原則展開為具體、可審查的條目。

#### II.1 一致的縮排單位 (Consistent Indentation Unit)
- 每一層邏輯區塊（迴圈、條件分支、函式主體）須以一致的縮排單位（如兩個或四個空格）呈現，同一份虛擬碼內縮排單位不得混用。

#### II.2 縮排即區塊邊界 (Indentation as Block Boundary)
- 區塊的起始與結束須可由縮排層級直接辨識，不依賴額外符號堆疊即可判讀巢狀深度。

#### II.3 巢狀深度控制 (Nesting Depth Control)
- 巢狀深度超過三層時，須考慮抽出為獨立步驟或子程序，以避免縮排過深導致可讀性下降。

### III. 高度抽象化，隱藏實作細節 (High Abstraction, Hiding Implementation Details)
虛擬碼應描述「做什麼 (What)」，而非「如何做 (How)」的底層實作細節。以下子章節將此原則展開為具體、可審查的條目。

#### III.1 以動作描述取代演算法展開 (Action Description over Algorithm Expansion)
- 陣列排序、雜湊計算、記憶體配置等底層操作，以一個具語意的動作描述（如「將清單排序」）取代逐步演算法展開。

#### III.2 細節僅在為核心重點時展開 (Detail Expansion Only When Core to the Topic)
- 僅在該底層細節本身即為演算法核心欲說明之重點時，才展開至該層級；其餘情況維持概念層級描述。

#### III.3 概念性錯誤處理描述 (Conceptual Error-Handling Description)
- 錯誤處理、例外情況以概念性描述（如「若查無資料則回傳空結果」）表示，不得使用特定語言的例外處理語法。

### IV. 命名具備語意化 (Semantic Naming)
所有變數、函式、步驟之命名須直接反映其用途或意圖。以下子章節將此原則展開為具體、可審查的條目。

#### IV.1 禁止無意義命名 (No Meaningless Naming)
- 禁止使用無意義的縮寫或單一字母命名（如 `x`、`tmp`、`flag1`），布林值命名須能表達其真偽意涵（如「是否已驗證」而非「狀態」）。

#### IV.2 動詞開頭的行為命名 (Verb-Led Behavioral Naming)
- 函式或步驟命名須以動詞開頭並表達其行為（如「計算總金額」「驗證使用者權限」）。

#### IV.3 領域詞彙一致性 (Domain Terminology Consistency)
- 命名須與所屬領域詞彙一致，避免同一概念在不同段落使用不同名稱指稱。

## 原則取捨 (Principle Trade-offs)

當本章各原則彼此衝突時，依下列優先順序解決：
1. 當「高度抽象化」與「結構清晰」衝突時（例如將細節抽象化後，流程反而因跳躍過多步驟而難以依縮排追蹤），優先確保讀者能依縮排結構完整追蹤流程，抽象化程度應調整至不犧牲結構可追蹤性為止。
2. 當「語言無關性」與「命名語意化」衝突時（例如某些語言慣用詞彙已成為業界通用術語，如「雜湊表」），可保留該通用術語作為概念性名稱，但不得連帶引入該語言的語法結構。
3. 當「高度抽象化」導致命名之語意變得模糊時，應優先服從「命名具備語意化」原則，重新拆解該抽象步驟直到命名足以表達意圖為止。
4. 若仍有疑義，優先服務於「跨語言讀者之可理解性」，並於虛擬碼附註中說明取捨理由。

## 合規要求 (Compliance Requirements)

依前述各子章節之詮釋，虛擬碼是否合規須依下列判準逐項核對：

- 語言中立性判準（對應 I.1–I.3）：確認虛擬碼未出現特定語言關鍵字、函式庫呼叫或型別關鍵字；流程控制與資料型別是否皆以通用詞彙表示。
- 結構清晰判準（對應 II.1–II.3）：確認縮排單位全文一致，且巢狀深度未超過三層；超過者是否已抽出為獨立步驟。
- 抽象層級判準（對應 III.1–III.3）：確認底層操作是否以語意化動作描述取代逐步展開；錯誤處理是否以概念性描述表示而非特定語言語法。
- 命名判準（對應 IV.1–IV.3）：確認命名無無意義縮寫、函式命名以動詞開頭、同一概念全文用詞一致。
- 審查紀錄：虛擬碼文件於納入設計文件前，須確認上述四類判準皆已核對；若因文件目的特殊而保留例外（如刻意展開演算法細節作為教學用途），須於文件中明確載明理由。

## Governance

本憲章適用於所有以虛擬碼形式撰寫之演算法說明、設計文件與程式碼審查前之邏輯草稿。

- 修訂程序：修訂者須說明新增或調整之原則、其適用情境，經專案負責人核准後生效。
- 版本控制政策：採語意化版本 (Semantic Versioning)。
  - 主版本：原則增刪或重新定義。
  - 次版本：新增具體指導方針或範例。
  - 修訂版：措辭澄清、錯字修正。
- 合規性審查：虛擬碼文件於納入設計文件前，須依「合規要求」章節確認是否符合上述四項原則。
